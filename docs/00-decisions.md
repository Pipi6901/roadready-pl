# Принятые решения (ADR)

Каждое решение фиксируется здесь с датой и обоснованием. Изменение решения — новая запись со ссылкой на отменяемую, старую не удаляем.

Статусы: `принято` / `предложено` (ждёт подтверждения) / `отменено`.

---

## ADR-001. Платформы: iOS и Android одновременно
**Дата:** 2026-07-20 · **Статус:** принято (решение заказчика)

Релиз в App Store и Google Play одним заходом. Кодовая база одна — React Native + Expo.

**Следствия:**
- Биллинг нужен кросс-платформенный (см. ADR-005), а не голый StoreKit.
- Цены в ТЗ указаны в GBP для Apple; для Google Play нужен зеркальный набор SKU и своя ценовая матрица.
- Каждый экран проверяется на двух платформах: системный шрифт (SF Pro на iOS / Roboto на Android), аппаратная кнопка «назад», TTS-голоса, поведение уведомлений.
- QA-прогон и наборы скриншотов для стора — двойные. Это заложено в оценку сроков.
- В ТЗ раздел 7 (NFR-07/08/09) написан только под iOS. Дополнено: Android 8.0+ (API 26), проверка на экранах от 360 dp, поддержка TalkBack наравне с VoiceOver.

## ADR-002. Без пользовательских аккаунтов, прогресс только локально
**Дата:** 2026-07-20 · **Статус:** принято (решение заказчика)

Регистрации и входа в MVP нет. Прогресс, XP, серия, статистика хранятся на устройстве. Подписка привязана к Apple ID / Google-аккаунту и восстанавливается через Restore Purchase.

**Обоснование:** снимает барьер на входе (обязательный логин в онбординге режет конверсию), убирает из продукта PII и резко упрощает соответствие GDPR.

**Следствия — правки к макету и ТЗ:**
- Экран ТЗ 3.7 «Регистрация / вход» из MVP **исключается**.
- Welcome Screen: ссылку «I already have an account» заменить на «Restore purchase».
- Settings: секция `ACCOUNT` (email, смена пароля, удаление аккаунта) **удаляется**. Вместо неё — «Restore Purchase» и «Reset progress» (локальный сброс с подтверждением).
- Profile: имя и аватар пользователь задаёт локально (или используется дефолт), «Learning since» считается от даты первого запуска.
- Требование Apple об удалении аккаунта неприменимо — аккаунта нет. В Privacy Policy это фиксируется явно.
- **Принятый риск:** переустановка приложения = потеря прогресса. Митигация — база прогресса лежит в каталоге, попадающем в iCloud Backup и Android Auto Backup, поэтому при восстановлении устройства прогресс возвращается. Кросс-девайс-синхронизация остаётся в фазе 2 (потребует аккаунтов).

## ADR-003. Бэкенд — Firebase, админка — собственная веб-панель
**Дата:** 2026-07-20 · **Статус:** принято (по ТЗ, раздел 4.2–4.3)

Firestore (метаданные и контент), Firebase Storage (медиа), Cloud Functions (сборка контент-пакетов), собственная веб-админка по объёму ТЗ 4.2: CRUD стран, тест-сеты с импортом из CSV/Excel, публикация и архивация, статусы переводов по языкам, управление медиа, soft delete, роли `content_editor` / `admin`.

**Следствия:**
- Админка — отдельное веб-приложение (Next.js) на Firebase Admin SDK, деплой на Vercel или Firebase Hosting. Доступ только по инвайту, без публичной регистрации.
- Публичного REST API из ТЗ 4.2 в буквальном виде не будет: приложение забирает не отдельные эндпоинты, а собранный контент-пакет одним файлом (см. ADR-004). Список эндпоинтов из ТЗ реализуется как контракт данных внутри пакета — функциональные требования соблюдены, стоимость чтений Firestore на порядок ниже.

## ADR-004. Контент доставляется пакетом-файлом, а не поштучными запросами
**Дата:** 2026-07-20 · **Статус:** предложено

Cloud Function по кнопке «Опубликовать» в админке собирает из Firestore статический пакет тест-сета (`manifest.json` + `content.json` + `translations/{locale}.json`), считает `version_hash` и кладёт в объектное хранилище. Приложение при первом запуске и при смене страны скачивает пакет одним файлом и работает офлайн; при наличии сети сверяет `version_hash` и дозагружает изменившиеся части.

**Обоснование:** 800 вопросов × 10 языков — это десятки тысяч документов. Поштучное чтение Firestore на каждой установке дорого и медленно; NFR-05 (p95 < 500 мс) на пакете-файле с CDN выполняется гарантированно, а офлайн-режим (FR-05) получается бесплатно как побочный эффект.

**Открытый вопрос:** где хранить медиа. По ТЗ — Firebase Storage, но исходящий трафик Google Cloud ≈ $0.12/ГБ. При NFR-03 (полный контент UK до 400 МБ) 10 000 загрузок = ~4 ТБ = ~$480/мес только за раздачу. Cloudflare R2 не берёт плату за egress: те же 4 ТБ — около $6/мес за хранение. Рекомендация: метаданные в Firestore, медиа и контент-пакеты — в R2 за CDN. Решение требует подтверждения заказчика (см. [08-risks-open-questions.md](08-risks-open-questions.md), OQ-3).

## ADR-005. Подписки — Adapty, линия 3.x
**Дата:** 2026-07-20 · **Статус:** предложено (подтверждается спайком)

Нужен слой, закрывающий App Store и Google Play разом, с серверной валидацией чеков и вебхуками. Проверены оба кандидата — RevenueCat и Adapty.

**Выбран Adapty 3.17.2.** Решающий аргумент: в Expo SDK 57 New Architecture обязательна, а у `react-native-purchases` 10.4.4 нет TurboModule-спеки и есть открытый баг с полным отказом модуля под New Arch (`NativeModules.RNPurchases is null`, воспроизводится стабильно). У Adapty поддержка New Architecture заявлена в сборочных файлах, есть Expo config plugin, и бесплатный порог вдвое выше. Детали сравнения — в [09-tech-stack.md](09-tech-stack.md), раздел 3.

Берётся линия 3.x, а не вышедшая 13.07.2026 версия 4.0: ей неделя, 4.0.1 уже чинил краш релизной сборки, а 3.17.2 вышла позже 4.0.1 и активно поддерживается.

Аккаунтов нет (ADR-002), поэтому пользователь — анонимный профиль, а перенос подписки после переустановки идёт штатным Restore Purchase.

**Условие:** решение подтверждается однодневным спайком до написания продуктового кода. Биллинг закрывается собственной абстракцией в одном модуле — смена вендора должна стоить день.

## ADR-009. Expo SDK 57 и обязательная New Architecture
**Дата:** 2026-07-20 · **Статус:** принято

Стартуем на Expo SDK 57 (React Native 0.86). Переход 56↔57 не-ломающий, риск нулевой, а к релизу через 3–4 месяца SDK 56 уйдёт за край окна поддержки.

**Следствие, определяющее выбор всех библиотек:** начиная с SDK 55 New Architecture обязательна, легаси-архитектура удалена. Любая библиотека без поддержки TurboModules работает только через переходный interop-слой или не работает вовсе — это уже отсеяло RevenueCat (ADR-005) и влияет на выбор Firebase-клиента (ADR-011).

## ADR-010. Озвучка — предгенерированные файлы вместо системного TTS
**Дата:** 2026-07-20 · **Статус:** предложено

FR-07 требует озвучки через системный TTS. Отклоняемся сознательно.

**Причина:** у `expo-speech` набор ограничений, ломающих сценарий: на iOS при включённом беззвучном переключателе звук не воспроизводится и при этом не возвращает ошибку — пользователь просто получает тишину; на Android нет паузы и возобновления, а список голосов пуст, если TTS-движок не установлен, что обычно для бюджетных и не-GMS устройств. Для приложения, где кнопка озвучки обязана быть на каждой карточке вопроса (ТЗ 10.8), такая лотерея неприемлема.

**Решение:** аудио генерируется заранее, кладётся в контент-пакет и воспроизводится через `expo-audio`. Одинаковое звучание везде, гарантированный офлайн, предсказуемое качество. `expo-speech` остаётся фолбэком.

**Стоимость решения невелика:** озвучивается только английский оригинал (ТЗ 10.5), а не девять переводов — это ~60 МБ на 730 вопросов, на фоне 400-мегабайтного пакета несущественно.

## ADR-011. Firebase-клиент в приложение не ставится
**Дата:** 2026-07-20 · **Статус:** предложено

Firestore остаётся серверной стороной: хранит контент, обслуживает админку, отдаёт фича-флаги и версии пакетов. Но **SDK Firebase в мобильное приложение не подключается**.

**Причина:** офлайн-персистентность Firestore в React Native не работает — кэш JS SDK построен на IndexedDB, которого в RN нет, и SDK молча уходит в память. Issue открыт с января 2024 и не закрыт. Альтернатива `@react-native-firebase` тянет обязательный dev-client, вес бандла и interop-риск под New Architecture (ADR-009).

**Это не потеря, а подтверждение ADR-004:** нам не нужен офлайн Firestore, потому что контент приходит файлом, а прогресс живёт в SQLite. Пакет качается по подписанной ссылке через `expo-file-system`, то есть хранилище может быть любым — что дополнительно усиливает аргумент за Cloudflare R2 (OQ-3).

## ADR-006. Hazard Perception в MVP выключен фича-флагом
**Дата:** 2026-07-20 · **Статус:** предложено

Симулированные hazard-клипы входят в лицензионный пакет DVSA, которого пока нет (ADR-007). Снимать или закупать своё видео под MVP — отдельный бюджет и сроки.

**Решение:** экран и логика замера времени реакции разрабатываются полностью (они на критическом пути и дороги в отладке), но в Practice Hub карточка показывается со статусом «Coming soon» и не открывается, пока фича-флаг выключен. Включается удалённо, без релиза, сразу после получения контента.

**Следствие:** из состава платной подписки на пейволле пункт «Hazard perception clips» на время убирается — обещать в оплаченной подписке недоступную функцию нельзя, это прямой путь к реджекту в App Review и к возвратам.

## ADR-007. Разработка ведётся на демо-банке вопросов
**Дата:** 2026-07-20 · **Статус:** принято (решение заказчика)

Лицензия DVSA не получена, заявка не подана. Использование вопросов DVSA без лицензии — уголовное правонарушение (ТЗ 8.1), поэтому до подписания договора реального банка в проекте нет.

**Решение:**
- Разработка идёт на демо-банке: ~50 собственных вопросов по открытым правилам Highway Code + дорожные знаки из набора Open Government Licence v3.0 (600+ изображений, требуется только указание источника).
- Схема данных и импорт проектируются сразу под формат лицензионного пакета DVSA (730 вопросов, 14 тем, пояснения, изображения), чтобы подмена контента прошла без переделки кода.
- Процесс лицензирования запускается **параллельно и немедленно** — он на критическом пути релиза: 10 рабочих дней на рассмотрение заявки, затем видеозвонок, договор, и отдельно — обязательное одобрение дизайна продукта со стороны DVSA.
- Роялти 13% от net sales закладываются в финансовую модель.

**Следствие:** дата релиза определяется не готовностью кода, а получением лицензии. Публикация с демо-контентом под видом официального банка недопустима: формулировки «official questions» и «licensed by DVSA» до подписания договора использовать нельзя.

## ADR-008. Тёмная тема проектируется отдельно
**Дата:** 2026-07-20 · **Статус:** предложено

NFR-10 и ТЗ 10.7 требуют тёмную тему с первого релиза, но в макете `screens.pen` описана только светлая палитра (24 экрана, тёмных вариантов нет).

**Решение:** вся вёрстка с первого дня использует только семантические токены (`bg`, `surface`, `text-primary`, …) — хардкод цветов в компонентах запрещён (ТЗ 10.2). Тёмная палитра выводится из светлой отдельной задачей дизайна до старта вёрстки экранов, проверяется по контрасту WCAG AA и фиксируется в [04-design-system.md](04-design-system.md).

## ADR-012. Подписки — RevenueCat как бэкенд, react-native-purchases не используется
**Дата:** 2026-07-29 · **Статус:** принято

Продукт требует именно RevenueCat (дашборд, вебхуки, аналитика), а не Adapty из ADR-005. Перед подключением проверен статус бага New Architecture, из-за которого ADR-005 в своё время отказался от RevenueCat.

**Спайк подтвердил, что баг всё ещё открыт:** актуальная `react-native-purchases` 10.5.0 по-прежнему не публикует `codegenConfig` (нет TurboModule-спеки), а issues [#1747](https://github.com/RevenueCat/react-native-purchases/issues/1747) и [#1739](https://github.com/RevenueCat/react-native-purchases/issues/1739) («`NativeModules.RNPurchases is null` под New Architecture», репродуцируется на связке, аналогичной нашей) остаются открытыми без ответа мейнтейнеров; попытка фикса (PR #1779) закрыта без мёржа 26.05.2026. New Architecture в Expo SDK 57 отключить нельзя (ADR-009), так что риск краша реален для любой сборки этого проекта.

**Решение:** не ставить `react-native-purchases` вообще. Покупку ведёт `react-native-iap` 15.x (SDK построен на Nitro Modules, которые физически требуют New Architecture — риска несовместимости нет по конструкции). Полученный чек/токен покупки отправляется в RevenueCat через задокументированную ими REST-интеграцию без SDK (`POST /v1/receipts`, см. [Using RevenueCat without the SDK](https://www.revenuecat.com/docs/migrating-to-revenuecat/sdk-or-not/sdk-less-integration)) — они валидируют покупку у Apple/Google и ведут учёт подписки, вебхуки и аналитику как обычно. Готовый пейвол-компонент `react-native-purchases-ui` не используется по той же причине; экран пейвола свой (`app/(onboarding)/paywall.tsx`).

Restore Purchase (обязателен по ADR-002, аккаунтов нет) реализован через `getAvailablePurchases()` react-native-iap с повторной отправкой найденных покупок в RevenueCat.

**Следствие:** `src/store/SubscriptionProvider.tsx` — реальная реализация вместо мока, `src/data/revenuecat.ts` и `src/constants/billing.ts` — новые модули. `PAYWALL_ENABLED` (src/constants/flags.ts) остаётся выключен до заведения проекта в RevenueCat и продуктов (SKU) в App Store Connect / Google Play Console — сейчас там плейсхолдеры.
